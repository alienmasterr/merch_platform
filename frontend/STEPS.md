# Frontend: звіт по кроках

Як запускати (один раз): `docker compose up -d postgres`, `npm install`, `cp .env.example .env`
(у `.env` можна поставити `PERSISTENCE=postgres`), `npm run migrate -w backend`, `npm run seed -w backend`.
Далі у двох терміналах: `npm run dev:backend` і `npm run dev:frontend`, відкрити http://localhost:5173.

Сторонні сервіси (LiqPay, Нова Пошта, SMTP) працюють як заглушки бекенду: доставка 70 грн,
ТТН `DEV-…`, листи друкуються в консоль бекенду, оплата підтверджується dev-кнопкою (крок 10).

## Крок 0. Підготовка фронтенду (A0.1)

**Зроблено**

- Прибрано демо Vite (лічильник, логотипи, App.css).
- `tsconfig.app.json`: `strict`, `noUncheckedIndexedAccess`; типи jest-dom для тестів.
- `vite.config.ts`: порт 5173 (strict), проксі `/api/*` → `http://localhost:3000/*` (без CORS), конфіг Vitest (jsdom).
- Скрипти: `test`, `test:watch`, `typecheck`, `test:e2e`, `gen:api`. Тепер кореневі `npm test` / `npm run typecheck` і CI
  перевіряють і фронтенд.
- Залежності: react-router, @tanstack/react-query, openapi-fetch; dev: vitest, Testing Library, jsdom, msw, Playwright.
  `openapi-typescript` не ставиться в проєкт (вимагає TypeScript 5, у нас 6) і запускається через `npx` у `gen:api`.
- Базові стилі (`index.css`): світла/темна тема, кнопки, поля, картки, таблиці.

**Як перевірити**

1. `npm run dev:frontend` → http://localhost:5173 показує заголовок «Merch Platform», консоль браузера без помилок.
2. `npm test -w frontend`, `npm run typecheck -w frontend`, `npm run lint -w frontend` зелені.
3. http://localhost:5173/api/health повертає `{"status":"ok"}` (проксі працює).

**Перевірив сам**: typecheck, lint, тести зелені; `/api/health` і `/api/catalog/categories` через проксі відповідають.

> Зауваження до бекенду (не моя зона): на Windows падає `config.test.ts > дефолти` — тест перевіряє
> `UPLOADS_DIR.endsWith('.data/uploads')`, а `path.join` на Windows дає `\`. Треба порівнювати через `path.join`.

## Крок 2. API-шар (A0.3, A1.2, A1.3)

**Зроблено**

- `src/api/schema.d.ts` згенеровано з `packages/contracts/openapi.yaml` (`npm run gen:api -w frontend`; перезапускати після змін OpenAPI).
- `src/api/client.ts`: типізований клієнт `openapi-fetch` + `unwrap()`, який повертає дані або кидає `ApiError`
  (`status`, `code`, `message`, `details`). Мережевий збій → `NETWORK_ERROR`, не-JSON 5xx (бекенд вимкнено) → `SERVER_UNAVAILABLE`.
- `src/api/errors.ts`: `describeError()` перетворює помилку на текст для UI (з деталями валідації zod).
- `src/api/types.ts`: короткі імена типів (`ApparelItem`, `Order`, …). `src/api/catalog.ts`: health, категорії, каталог, товар.
- Індикатор «API працює / API недоступний» у шапці (опитує `/health` кожні 10 с).
- MSW для тестів: `src/test/server.ts` (обробники за замовчуванням), `src/test/fixtures.ts`. Будь-який незамоканий запит у тесті = помилка.
- Правило: компоненти не викликають `fetch`, лише функції з `src/api/`.

**Як перевірити**

1. При запущеному бекенді в шапці зелена крапка «API працює».
2. Зупинити бекенд (Ctrl+C) → протягом ~10 с крапка стає червоною «API недоступний». Запустити знову → зелена.
3. `npm test -w frontend`: тести клієнта (дані, query-параметри, 404 → ApiError, 500 без JSON, мережевий збій) зелені.

**Перевірив сам**: 14 тестів, typecheck, lint; у браузері індикатор зелений.

## Крок 4. Сторінка товару

**Зроблено**

- `/product/:id`: силует у кольорі товару, тип, наявність, ціна, підготовка до друку, склад, особливості
  (капюшон/кишені, талія/довжина, тип аксесуара), зони друку.
- Вибір кольору й розміру серед варіантів того самого товару. Немає точної пари → зберігається те, що щойно обрали
  (клік «L» на білій M відкриє чорну L, бо білої L немає). URL змінюється на id варіанту.
- «Створити дизайн» → `/customizer?baseItemId=<id>`; для товару не в наявності кнопки немає, є попередження.
- 404 → «Товар не знайдено»; запити з помилкою 4xx більше не повторюються (React Query повторює лише 5xx/мережу).

**Як перевірити**

1. Каталог → картка «Футболка базова» → відкривається товар, кнопка «Створити дизайн» веде на `/customizer?baseItemId=…`.
2. Клік «Білий» → URL `/product/tee-white-m`, розмір M. Клік «L» → `/product/tee-black-l`.
3. http://localhost:5173/product/nope → «Товар не знайдено».
4. У панелі адміна (крок 13) або через `curl -X PATCH` зняти товар з наявності → кнопки немає.

**Перевірив сам**: 37 тестів; у Chromium пройшов каталог → товар → зміна розміру → 404.

## Крок 5. Завантаження принта (A2.1)

**Зроблено**

- `features/customizer/printFile.ts`: `validatePrintFile` (png/jpg/jpeg/webp/svg, MIME image/*, не порожній, ≤ 20 МБ;
  ті самі правила, що на бекенді), `readImageAspect` (пропорції картинки для стартового розміру принта).
- `/customizer` без параметрів показує вибір виробу (лише ті, що в наявності); `/customizer?baseItemId=…` відкриває конструктор.
- Вкладки зон друку (лише дозволені для виробу: футболка: груди/спина/рукав, штани: штанини, аксесуари: лицьова сторона).
- Зона перетягування + кнопка «оберіть файл». Невалідний файл → червоне повідомлення, запит на сервер не йде.
  Валідний → `POST /customizer/uploads`, принт з'являється на мокапі. Помилку сервера теж видно.

**Як перевірити**

1. Каталог → товар → «Створити дизайн» (або меню «Конструктор» → обрати виріб).
2. Перетягнути `.gif` або `.pdf` → «Формат … не підтримується». У DevTools → Network немає запиту `uploads`.
3. Файл понад 20 МБ → «Файл завеликий». Порожній файл → «Файл порожній».
4. PNG/SVG → запит `POST /api/customizer/uploads` (201), принт на грудях. Файл лежить у `.data/uploads` і відкривається за URL.

**Перевірив сам**: 10 тестів `validatePrintFile`; у Chromium: gif і 20+ МБ відхилено без запитів до API, SVG завантажено.

## Крок 6. Позиціонування (A2.2)

**Зроблено**

- `features/customizer/placement.ts` (чисті функції): межі зон `PLACEMENT_LIMITS` (як на бекенді), `clampToArea`
  (та сама умова, що `validateBounds` на бекенді: |зміщення| + розмір·масштаб/2 ≤ межа/2), `calculatePosition`
  (де малювати принт на полотні), `fitToArea` (стартовий розмір зі збереженням пропорцій), `estimatePrintCost`.
- Редюсер `customizerState.ts`: усі зміни (масштаб, зміщення, перетягування) проходять через `clampToArea`, тому
  принт фізично не може вийти за зону, а бекенд не поверне 400 «Print exceeds the area».
- Мокап `PrintCanvas` (SVG, 1 одиниця = 1 мм): силует, пунктирні зони (активна підсвічена), принти.
  Перетягування мишею/пальцем, стрілки (5 мм, Shift+стрілка 20 мм). «Спина» показується на виді ззаду.
- Панель: технологія друку, слайдери масштабу і X/Y (діапазони рахуються від меж зони), «По центру», «На всю зону»,
  «Замінити», «Видалити», орієнтовна ціна принта.

**Як перевірити**

1. Завантажити принт на «Груди», потягнути мишею далеко за край → принт зупиняється на межі пунктирної зони.
2. Клік по принту, стрілки/Shift+стрілки → рухається; значення «Зміщення по X/Y» змінюються.
3. «Рукав» → завантажити → «На всю зону» → принт 100×50 мм (зона 100×100). Слайдер масштабу не дає більше.
4. «Спина» → бейдж «Вигляд ззаду».

**Перевірив сам**: 29 тестів чистих функцій + 9 тестів редюсера; у Chromium перетягування на 2000 px упирається
в межу (зміщення X 59.9 мм при принті 180 мм у зоні 300 мм), стрілки зсувають на 5/20 мм.

## Крок 7. useCustomizer і збереження (A2.3, A2.4)

**Як перевірити**

1. Додати принт на груди і рукав → «Зберегти дизайн» → зелене «Дизайн збережено», прев'ю, таблиця цін.

**Перевірив сам**: 6 тестів хука (валідація без запиту, завантаження в активну зону, помилка сервера, тіло запиту
збереження, скидання після правки), 7 тестів сторінки, 3 тести `uploadPrint`; у Chromium збережено дизайн із 2 принтами:
орієнтовна ціна 455,5 грн = ціна від бекенду 455,5 грн.

> Примітка про тести: у Vitest+jsdom multipart-запит із jsdom-файлом не проходить через fetch (обмеження інструмента,
> не коду), тому в тестах хука й сторінки `uploadPrint` підмінено (`src/test/mockUpload.ts`), а сам запит перевіряє `src/api/customizer.test.ts`.

## Крок 10. Оплата (A3.3)

**Зроблено**

- На сторінці замовлення в статусі `CREATED` кнопка «Оплатити через LiqPay» → `POST /orders/:id/checkout` →
  перехід на `checkoutUrl` (зі справжніми ключами це сторінка LiqPay; без ключів бекенд одразу повертає на `/payment-result`).
- `/payment-result?orderId=…`: опитує замовлення кожні 2 с. Поки `CREATED` → «Очікуємо підтвердження оплати»,
  після webhook → «Оплату N грн отримано. Чек надіслано на …».
- **Лише в режимі розробки** (`npm run dev`, у production-збірку не потрапляє) на цій сторінці є жовтий блок
  «Імітувати успішну оплату»: фронтенд підписує callback dev-ключем заглушки бекенду (той самий SHA-1-підпис, що в LiqPay)
  і шле його на `/payments/webhook`. Це замінює README-команду з `tsx` + `curl`. Зі справжніми ключами LiqPay такий підпис відхиляється.

**Як перевірити**

1. Відкрити створене замовлення → «Оплатити через LiqPay» → адреса `/payment-result?orderId=…`, видно спінер.
2. «Імітувати успішну оплату» → за ~2 с зелене «Оплату … отримано».
3. У консолі бекенду рядок `[email] to=… subject="Чек за замовлення …"`.
4. Повторно натиснути кнопку на іншій вкладці / ще раз надіслати callback → статус не змінюється (webhook ідемпотентний).

**Перевірив сам**: 2 тести підпису (збігається з `crypto.createHash('sha1')` як на бекенді), 3 тести сторінки результату,
тест редіректу; у Chromium з реальним бекендом: оплата → `PENDING_REVIEW`, лист-чек у консолі бекенду.
